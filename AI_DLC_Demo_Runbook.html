What is AI DLC

~3 min

Data AI Development Life Cycle — a working proof of concept, not a slide. Shows, not describes, how an AI-assisted delivery loop runs.

  • The loop: Jira Ticket → Technical Design Document (ADR/SDR) → Implementation & Tests → PR → Jira Update.
  • Goal: enforce "define before build" discipline — safe, human-in-the-loop, at AI speed.
  • Repo constitution lives in CLAUDE.md: it overrides default agent behavior for this project.
Scope check: working POC on N-iX-owned accounts, synthetic data only — no Basware systems or data touched. Toy AP-automation domain mirrors Basware's world, not real Basware logic. Out of scope today: CI/CD automation, multi-domain model, production governance.

How the data is generated — and what the sparsity means

Synthetic CSVs are produced by a per-tenant generator: each invoice row is independently assigned a populated or empty customer_id using a fixed probability draw per tenant (80% / 30% / 10%). This isn't noise — it's a deliberate stand-in for two business flows AP systems handle at once:

  • Procure-to-Pay (P2P) — the tenant is the buyer. When Krones AG buys automation parts from Siemens, Krones is the customer in that transaction — but Krones is also the tenant running the AP system. There's no separate "customer" entity to record: the tenant already is the customer. So customer_id is legitimately empty — there's nothing distinct to put there.
  • Order-to-Cash (O2C) — the tenant is the seller. When Krones sells finished bottling equipment to Heineken, Heineken is a real, distinct counterparty — a customer separate from the tenant. Here customer_id genuinely should be populated, because it identifies who Krones is selling to.

Why the population rate differs by tenant:

TenantPopulatedBusiness story
KRN80%Mostly buying components from suppliers (P2P) — the populated field represents the rarer sales-side invoices.
GDS30%A genuine mix — logistics firms both procure fleet/equipment and bill shippers directly, so both flows coexist.
STK10%Overwhelmingly procurement-driven (buying inventory from suppliers) — almost no distinct "customer" to track.

The real problem this dramatizes: building dim_customer naively forces a silent choice between two incompatible readings of "customer" — the tenant itself (P2P) or the transaction counterparty (O2C). A metric like touchless invoice rate per customer means something different under each reading. That's the "define before build" moment DP-15 exists to force into the open before code gets written against an unstated assumption.

Data model: 7-table Kimball star schema
  • Fact table: fact_invoice_transaction (470 rows) — one row per invoice, grain = invoice line per tenant.
  • Dimension tables: tenant (3 rows), supplier (~36: natural key trap — composite (tenant_id, supplier_id) because each tenant's ERP assigns codes independently), date (365: role-played across invoice/due/payment), invoice status (6 static), cost center (~17: composite tenant-scoped key), payment terms (5 static).
  • Deliberate omission: no dim_customer — the source field is semantically ambiguous (customer = the tenant itself in procure-to-pay flows, or customer = transaction counterparty in order-to-cash flows?) and inconsistently populated. This is the "define before build" moment.
Business metrics in semantic layer
  • Touchless Invoice Rate: % of invoices processed without manual intervention — core Basware value proposition.
  • Exception Rate: % of invoices requiring manual review — inverse of process health.
  • Approval Cycle Time: average days from receipt to approval sign-off.
  • Days Payable Outstanding: amount-weighted average days from invoice to payment.
  • Total Spend: aggregated invoice value, sliceable by supplier, cost center, or tenant.
Two natural key traps in the build
  • Supplier scoping: supplier code is tenant-local. Two tenants may both have SUP-1001, representing entirely different suppliers. Joins must enforce (tenant_id, supplier_id) as the natural key.
  • Cost center scoping: likewise, cost center codes are tenant-scoped, requiring composite key joins to prevent cross-tenant collisions.

AI DLC artefact structure

~4 min

What makes the agent behave like a team member, not a generic chatbot.

CLAUDE.md

The workflow contract: repo layout (ADR-001), branch/commit conventions, phase gates. Overrides default behavior.

.claude/agents/

6 specialist subagents — data-architect, data-modeller, pipeline-engineer, unit- / integration-test-engineer, pr-reviewer. Each scoped to a role.

.claude/skills/

Reusable Databricks know-how: CLI auth, DABs, jobs, pipelines — loaded on demand, not baked into every prompt.

Configs

settings.json (model, MCP servers), databricks.yml (bundle targets: dev/test/staging/prod).
